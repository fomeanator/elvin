# 3D как часть языка

Цель: **автор собирает трёхмерную сцену прямо в `.lvns`**, не открывая Unity.
Не «движок умеет показывать 3D-набор, который кто-то собрал», а «место в игре
описывается текстом так же, как реплика или выбор».

Отсюда требование, из которого следует всё остальное:

> Понятий должно быть мало, и каждое пишется одной строкой.

Мы не повторяем Unity целиком. Unity — универсальный движок, и цена этой
универсальности — редактор, сцены, префабы, материалы, слои, компоненты. Для
новеллы 90% этого не нужно: физики нет, камера ставится автором, стиль один на
всю игру. Берём фундамент и выбрасываем остальное.

---

## Семь фундаментальных вещей

Любая трёхмерная сцена — это ровно они. Больше ничего в основании нет.

| # | Вещь | Что это | Чем задаётся у нас |
|---|---|---|---|
| 1 | **Пространство** | метры, ось Y вверх, начало — точка сцены | неявно, общее для всего |
| 2 | **Тело** | то, что занимает место: примитив, модель, плоская фигура | `o3d` |
| 3 | **Вид** | цвет, текстура, прозрачность, свечение | поля `o3d` |
| 4 | **Место** | где стоит, как повёрнуто, какого размера | поля `o3d` |
| 5 | **Свет** | солнце, заполняющий, точечный; тени | `light` |
| 6 | **Атмосфера** | небо, туман, общий свет | `light kind=sky/fog` |
| 7 | **Взгляд** | камера: место, направление, обзор | `bg3d` (уже есть) |

Движение — не восьмая вещь: это те же свойства во времени (см. ниже).

## Две новые команды

Каждая команда языка стоит дорого: её надо реализовать в рантайме Unity, в
компиляторе, в валидаторе, описать в документации и удержать одинаковой во всех
реализациях. Поэтому их ровно две — всё остальное ложится в их поля.

### `o3d` — тело в сцене

```
o3d id=камень shape=box pos="0,0,3" size="1,0.6,1" color="#6b7078"
o3d id=факел shape=cylinder pos="-2,0,4" size="0.1,1.6,0.1" color="#3a2a1a"
o3d id=огонь shape=sphere pos="-2,1.7,4" size="0.3" color="#ffb347" glow=2
o3d id=стена model=wall_stone pos="0,0,8" yaw=90
o3d id=знак sprite="/content/signs/warn.png" pos="1,0,5" height=1.2
o3d id=камень off
```

| Поле | Смысл |
|---|---|
| `shape` | примитив: `box`, `plane`, `sphere`, `cylinder`, `cone`, `disc` |
| `model` | имя модели из бандла набора или библиотеки |
| `sprite` | плоская фигура: картинка, развёрнутая к зрителю (то же, что `obj in3d`) |
| `pos` | место в метрах, `"x,y,z"`; `y=0` — уровень земли |
| `size` | размер в метрах: одно число (куб) или `"x,y,z"` |
| `yaw`/`pitch`/`roll` | поворот в градусах |
| `color` | цвет `#rrggbb`; для `sprite` — подкраска |
| `texture` | картинка на поверхности |
| `normal`, `bump`, `tiling` | карта нормалей, сила рельефа и метров на повтор текстуры |
| `edge`, `ruts`, `wet` | только `shader=road`: неровность края, сила колей и их влажность, 0…1 |
| `alpha` | прозрачность 0…1 |
| `glow` | свечение: 0 — нет, 1…4 — сила |
| `ground` | `1` — посадить основанием на грунт под точкой |
| `shadow` | `0` — не отбрасывать тень (по умолчанию отбрасывает) |
| `on_click` | метка перехода по нажатию |
| `off` | убрать тело |

### `light` — свет и атмосфера

```
light kind=sun angle="50,-30" color="#fff4e0" power=1.1
light kind=fill color="#3a4a6b" power=0.35
light kind=point id=костёр pos="-2,1.6,4" color="#ff9a3c" power=2 range=6
light kind=fog color="#1b2430" near=6 far=40
light kind=sky top="#0b1020" bottom="#2a3550"
light kind=point id=костёр off
```

| Поле | Смысл |
|---|---|
| `kind` | `sun`, `fill`, `point`, `spot`, `fog`, `sky` |
| `angle` | для солнца: `"высота,азимут"` в градусах |
| `pos` | для точечного: место в метрах |
| `color`, `power` | цвет и сила |
| `range` | радиус точечного, в метрах |
| `near`/`far` | туман: начало и конец; у прожектора `near` — угол раствора |
| `flicker` | дрожание лампы, 0…1: живой огонь не горит ровно |
| `top`/`bottom` | цвета неба вверху и у горизонта |

## Шейдеры — это и есть стиль игры

Мы не заготавливаем библиотеку ассетов. Мы держим библиотеку ШЕЙДЕРОВ, и она же
задаёт вид игры: любой объект — примитив, купленная модель, сгенерированная
болванка — перекладывается на наши материалы (`Lvn3DStyle`). Геометрия, текстура
и цвет сохраняются; блеск, микрорельеф и чужая модель освещения отбрасываются.

| `shader=` | Для чего |
|---|---|
| `toon` | по умолчанию: ступени света, цветная тень, ободок по силуэту |
| `wind` | растительность: вершинное качание, `wind=` — сила в метрах |
| `aura` | энергия вокруг тела: Френель, пульс, текущие полосы |
| `water` | рябь вершинами, два слоя бликов, цвет глубины |
| `glass` | стекло, лёд, кристалл, барьер |
| `dissolve` | растворение с горящим краем, `dissolve=0…1` |
| `fire` / `smoke` | пламя и дым: градиент по высоте, мягкий край, без геометрии |
| `triplanar` | текстура по мировым осям — БЕЗ UV-развёртки |
| `road` | грунтовая дорога: неровный край, колеи и дозированная влажность |
| `unlit` | ровный цвет без освещения |

Плюс наше небо (`light kind=sky`) вместо стандартного skybox: градиент, светило
по направлению `sun`, звёзды по темноте, дымка у горизонта.

Ограничение стилем — не потеря, а то, что делает кадр целым. Можно загрузить что
угодно, но выглядеть оно будет по-нашему.

## Глубина резкости

```
bg3d focus=8 dof_range=3 dof=1.6
```

Резко в восьми метрах, ±3 метра тоже резко, дальше мягко тает. Это сильнее
любой геометрии отличает кадр от «картинки из игры»: объектив держит в фокусе
одну плоскость, и глаз читает это как камеру, а не как рендер. Заодно расфокус
показывает, куда смотреть, — половина режиссуры для кадра, который
рассматривают долго.

Живёт проходом НА КАМЕРЕ набора (`Lvn3DDofPass`), а не ручным Blit после съёмки:
в живом режиме камера рендерит сама, и ручной проход просто не вызывался бы —
расфокус был бы виден на неподвижном кадре и пропадал, стоило сцене ожить.

## Движение

Движение — не восьмая фундаментальная вещь, а те же свойства во времени:

```
o3d id=дверь yaw=90 dur=1.2        # переход в новое состояние за 1.2 с
o3d id=призрак dissolve=1 dur=2    # растворился
o3d id=монета spin=120             # вращается, градусов в секунду
o3d id=фонарь bob=0.15 bob_speed=0.5   # покачивается, метры
o3d id=сердце pulse=0.2 pulse_speed=1.5 # пульсирует размером
```

Пока что-то движется, кадр снимается сам. Когда всё замерло — съёмка
прекращается: неподвижная картинка не должна стоить шестидесяти кадров в
секунду.

## Отношения вместо координат

```
o3d id=фонарь model=lantern pos="2,0,5"
o3d id=скамья model=bench near=фонарь dist=1.4 side=left
o3d id=свеча  shape=cylinder on=надгробие
```

Автор думает о сцене отношениями — «скамья у фонаря», «свеча на могиле», — а
не координатами. Перевод в метры механический, и ошибается на нём тем чаще,
чем больше объектов: надо ПОМНИТЬ, где фонарь.

Тем же путём идут исследовательские генераторы сцен (Holodeck, I-Design):
модель описывает отношения, решатель считает позы. Разница в цене: им нужен
оптимизатор ограничений, нам — нет, наши отношения однозначны и считаются
арифметикой в компиляторе. Рантайм получает готовый `pos`.

## Сетка координат

```
grid 2
o3d id=склеп model=crypt-a pos="-3,0,6"    # клетка (−3, 6) = (−6, 12) м
grid off
```

Метры непрерывны, и промахнуться в них можно на любую долю — а автор-нейросеть
не видит кадра и проверить себя не может. Клетки делают расстановку
арифметикой: целые числа, видимые глазом, и **предупреждение при сборке**, если
два тела попали в одну клетку («склеп (строка 11) и фонарь (строка 14)»).

Дробная часть остаётся подстройкой внутри клетки — зернистость никуда не
делась, но проверка занятости смотрит на целую часть и не поднимает ложных
тревог. `size` при этом всегда в метрах: рост тела клетками не мерят.

Как и карта, это конструкция ВРЕМЕНИ КОМПИЛЯЦИИ — рантайм получает обычные
метры и о сетке не знает.

### Две ступени

```
grid 2 sub 10
```

Клетка два метра, внутри — подсетка 10×10 по двадцать сантиметров. Крупное
(склеп, дерево) ставится целыми клетками, мелочь (свеча, венок) — дробными;
координаты прилипают к подсетке, поэтому `1.47` становится `1.5` и мусорные
хвосты не копятся.

Проверки при этом РАЗНЫЕ, и в этом весь смысл: два склепа в одной клетке —
ошибка, две свечи в одной клетке — норма, две свечи в одной подклетке — снова
ошибка. Крупное от мелкого движок отличает сам, по габариту тела в плане.

`lvnconv plan -i сцена.lvns` печатает вид сверху теми же клетками: одна команда
показывает всю расстановку, `#` отмечает столкновения, `˙` — клетку с мелочью.
`-zoom "1,3"` разворачивает эту клетку в подсетку.

Тот же приём применяют в исследованиях генерации сцен языковыми моделями
(SpatialGrammar сводит сцену к плану сверху и восстанавливает позы
компилятором) — по той же причине: непрерывные метры модель не удерживает, а
дискретные клетки удерживает.

## Карта отдельным файлом

Место рисуется символами, а не координатами — деревню из сорока домов иначе не
написать и не поправить. Файл `maps/деревня.lvnmap`:

```
tile 2

. = ground color=#3d4a35
# = box size="2,3.2,2" color=#6b5b45
T = cone size="1.8,6,1.8" color=#1d3526 shader=wind wind=0.15
~ = plane size="2,1,2" color=#2f5d6b shader=water
@ = camera

карта:
....TTT........TTT....
..T....######...T.....
..~~~..#....#....T....
..~~~....@.......T....
```

В новелле — одна строка: `map "maps/деревня.lvnmap"`.

Это конструкция ВРЕМЕНИ КОМПИЛЯЦИИ: карта разворачивается в обычные `o3d` со
списком точек (`at="x,z;x,z;…"`), рантайм о картах не знает. Сто деревьев
остаются одним мешем и одним материалом.

## Что уже есть и не меняется

- `bg3d` ставит камеру: `x y z pitch yaw fov`, качание `sway`, ходьбу `walk`.
  Новое поле — `build=1`: **пустая сцена**, которую наполняет скрипт (без
  готового набора из бандла).
- `obj … in3d=1 world="x,y,z" world_height=1.8` — плоская фигура в сцене.
  Остаётся как есть: это тот же `o3d sprite=`, только для персонажей, у которых
  уже есть свой арт, позы и анимации.
- `anim` двигает свойства во времени — в том числе тела сцены.

## Живой мир — базовый режим

Кадр замирает только на диалоговой паузе; основной геймплей идёт в работающем
мире. Поэтому живой режим не «терпим», а обеспечен бюджетом: масштаб буфера
подстраивается под то, что устройство успевает (просело ниже ~42 к/с — уступаем
резкостью, есть запас — возвращаем). Красивая картинка — это в первую очередь
ПЛАВНАЯ картинка.

## Что проверяется при сборке

Сцена бывает синтаксически безупречной и при этом пустой на экране — а автор
(тем более автор-нейросеть) видит это последним. Компилятор говорит об этом
сам:

| Проверка | Что ловит |
|---|---|
| строка похожа на команду | опечатка в имени команды — строка ушла бы игроку репликой |
| повтор `id` | второй `o3d` двигает тело, а не создаёт второе |
| имя модели | `model=crypt-x` при `crypt-a` в наборе, с подсказкой |
| занятость клетки | два тела в одной клетке, по следу тела |
| видимость | тело позади камеры, за туманом или внутри камеры |
| свет | в сцене нет ни одного источника — кадр чёрный |
| размеры | сантиметры или километры вместо метров |
| цвет | `red` вместо `#rrggbb` |
| бюджет | больше 400 тел или 24 цветов |
| границы чисел | значение вне разумного порядка (таблица `internal/lvns/limits.go`) |

Границы намеренно широкие: задача не навязать вкус, а поймать ПОРЯДОК — 0.05
вместо 5, 300 вместо 30. У каждой границы в таблице записана причина, и она
попадает в текст предупреждения целиком: автор читает «выше восьми выжигает
кадр в белое», а не «значение вне диапазона».

Нарочно странный кадр объявляется прямо в строке:

```
bg3d build=1 x=0 y=1.6 z=-5 fov=8   // lvn-ok: подзорная труба
```

Выход обязателен. Линтер без него становится врагом: ложная тревога в каждой
сборке приучает не читать предупреждения, и настоящие тонут вместе с ней.

Состав наборов компилятор берёт из манифеста: сборщик бандла записывает туда
имена объектов набора, и `o3d model=…` сверяется с этим списком.

## Правила, которые держат сцену дешёвой

Они те же, что в [правилах наборов](3d-set-rules.md), и здесь ужесточаются одним
пунктом: **сцена, собранная скриптом, платит за каждое тело отдельным вызовом
отрисовки**. Поэтому:

- Одинаковые тела с одинаковым видом Unity сливает автоматически (инстансинг
  включён на наших материалах) — двадцать одинаковых камней стоят почти как
  один.
- Разноцветные тела дороже: цвет создаёт свой материал. Держите палитру
  короткой — это и правило вкуса, и правило скорости.
- Больше 150 тел в одной сцене — стоп, дальше нужен собранный набор.

## Почему примитивы, а не «импортируйте модель»

Тот же ответ, что у Roblox: **низкий порог входа важнее фотореализма**. Из
коробки, комнатой из шести плоскостей и десятком коробок, автор собирает
узнаваемое место за пять минут и без художника. Дальше, когда место того стоит,
на него кладут модели — и они встают в то же пространство, теми же метрами.

Примитивы мы строим сами, вершинами, а не через `GameObject.CreatePrimitive`:
встроенные ресурсы Unity вырезаются сборщиком, и в собранной игре примитив
приезжает без меша. Этот урок уже оплачен — фигурами, которые в редакторе
стояли, а на устройстве исчезали.
